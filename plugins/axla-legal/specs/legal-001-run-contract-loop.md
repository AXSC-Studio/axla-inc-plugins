# legal-001 · run contract loop
> 契約書（まず NDA）を、ループエンジニアリングで「受け取り → Axla の直し → 相手との往復 → 署名」まで回す決まり。仕組み（道具・指示文・LEGAL.md）と台帳は git、契約の実物は Drive に分ける

**実装対象**: scripts/（道具）・prompts/（指示文）・loop/legal/（LEGAL.md）・loop/legal/register.csv（台帳）・Google Drive の Legal/ 配下（契約の実物）・Gmail（下書きまで）
**起源**: 1件目の NDA（相手の雛形・入口 A）を回した結果と、その後の設計の見直し（代表承認）をまとめたもの。名前は暫定
**ステータス**: L1（spec 起票・Human Judge 確認待ち）

---

## Requirements

- The system shall 契約ごとに Drive の契約フォルダを1つ作り、中身を下の「Drive の構成」のファイルだけにすること（社内の周回ごとにファイルを増やさない）
- The system shall 契約書の版を、相手との境目をまたいだ回数（v1、v2、…、Final、Signed）で名前に付けること。社内の周回の数は名前に出さないこと
- The system shall Axla の直しを、相手の原本 .docx に変更履歴（作成者：Analy┊Axla Inc.。区切りは全角の「┊」U+250A）と理由のコメントを入れた形で作り、その版の社内用の gdoc（`F_vX.Y.Z_Axla Comments`）に同じ ID のまま取り込むこと。相手に送る .docx は、変更をすべて反映し、コメントと作成者などの情報を消した**清書**にすること（scripts/ の手順）
- The system shall 内側のループで、検証役（prompts/reviewer-prompts.md）を並列に動かし、止める条件（致命的 0件）を満たすまで回すこと。5周しても満たさなければ G1 に上げること
- The system shall 中間ループの間、LEGAL.md（loop/legal/LEGAL.md）を読むだけにし、書き換えないこと。学びは Loop Log に書き、Signed の後に外側のループで PR として反映すること
- The system shall 各周の検証の結果・変更点と理由・G1 の答えを `loop/legal/contracts/<契約 ID>/loop-log.md` に追記し、いちばん上に「いまの状態と次の一手」を置くこと
- The system shall 返信は相手のメールの続き（同じスレッドへの返信）の下書きとして作ること。添付は代表が手で付け、送信も代表が押すこと
- The system shall NOT 契約フォルダを相手と共有しないこと。送る版は添付で送る
- The system shall NOT 契約の本文・相手の社名・担当者名・住所・changes JSON を git に入れないこと

## Non-goals

- 電子契約サービスの操作・署名そのもの（G2）
- RAG（検索の仕組み）は当面作らない。LEGAL.mdと指示文は、子セッションが毎回全文を読む
- NDA 以外の契約のLEGAL.md（同じループの形で回すが、LEGAL.mdは契約の種類ごとに loop/legal/ に別に育てる）

## 三層のループ

| 層 | 1周 | 止まるとき |
|---|---|---|
| 内側 | 起草 → 検証（4体を並列）→ 直す | 致命的 0件。5周しても 0件にならない、または事業の判断が要るときは G1 |
| 中間 | Axla の直しを送る → 相手の返事 → 受けるか直すか（内側のループをもう一度） | 署名済みの PDF がフォルダに入ったとき（Signed） |
| 外側（BML） | 契約をまたいで、LEGAL.mdと指示文を直す（PR） | 契約が1件 Signed になるごと |

- 1往復で締結することを優先する。直すのは、Axla が実害を受けうるものと、双方の扱いをそろえるものだけ（loop/legal/LEGAL.md の「使い方」）。LEGAL.mdは 0.10.0。専門家に確かめていない点は、LEGAL.md冒頭の「宿題リスト」の当面の扱いで起草してよい。宿題は外側のループで一度だけ専門家に確かめ、LEGAL.mdに書き込んで消す。
- 中間ループの間は、LEGAL.mdは読むだけ。LEGAL.mdの外の判断は G1 に上げ、学びは Loop Log に書く。

## 入口（トリガー）

ループは見回りではなく、イベントで始める。

- **入口 A（受信）**：相手から契約書付きのメールが届く。パスワード付きの添付は、別のメールや本文の決まりに従って開く。決まりが分からなければ代表に聞く。
- **入口 B（発信）**：代表が「〇〇社と NDA」と言う。Axla の雛形をコピーして始める。
- どちらも「契約フォルダに v1 の .docx と、読む用の gdoc がそろった状態」に合流し、そこから同じループに入る。

## 入口の自動検知（試運転）

相手の返事を、人が気づく前にループが拾うしくみ。いまは**読むだけの試運転**（判定して知らせるところまで。返信や Drive の書き込みはしない）。

```
相手からのメール
  → Gmail のフィルタ（from:<相手のドメイン> → ラベル「Legal/返信あり」）
  → Apps Script（scripts/apps-script/notify_reply.gs、1分ごと）がそのラベルのスレッドを見つける
  → claude.ai のクラウドの見張りタスク（ルーティン）の /fire に POST する。本文はスレッド ID だけ（メールの中身は送らない）
  → 成功したら、ラベルを「Legal/通知済み」に付け替える（同じ返事で何度も起こさない。失敗したらラベルを残し、次の1分でもう一度）
  → 見張りタスクが、スレッドを読んで返事の種類を A〜E に分け、司令塔に知らせる
```

- 見張りタスクは、API での起動のほかに、毎朝の予備の起動も持つ（Apps Script が止まっていても1日1回は見る）。
- 合鍵（API のトークン）は、Apps Script のスクリプトのプロパティ `ROUTINE_TOKEN` に人が貼る。コードにも git にも書かない。
- 見張りタスクが使える道具は、Gmail の**読む道具だけ**にする。書き込み系（下書き・送信・ラベル・削除など）は `disallowed_tools` で禁止する。

試運転で分かったこと：

- (a) 道具を絞るのに `permitted_tools` は効かなかった。`disallowed_tools` で絞れた。
- (b) `allowed_tools` に入れていない Bash も動いた。禁止したいものは、`disallowed_tools` に明示する。
- (c) 大きいスレッドは get_thread の結果が溢れる。search と get_message（1通ずつ）で読む。
- (d) 返事が別のスレッドで来ることがある（会議の承諾が、別スレッドで届いた）。スレッド ID だけで追わず、相手のドメインと日時でも探す。

## 版の決まり

契約書の版は **vX.Y.Z** の三層で数える。ファイル名にも出す。

| 層 | 数えるもの | いつ上がるか |
|---|---|---|
| X | **外側ループが回った数**（LEGAL.md の世代） | 契約が Signed になり、学びを PR でマージしたら +1。LEGAL.md 自体の版もこの世代の整数で表す |
| Y | **相手との境目をまたいだ回数** | v?.1.?＝相手の原本（入口 B なら Axla の雛形）、v?.2.?＝Axla が送る直し、v?.3.?＝相手の返事 … |
| Z | **その契約の内側ループの通算周回** | 検証を1周回すたびに +1。Y が上がってもリセットしない |

- ファイル名の版は、そのファイルを**受け取った・送ったときの数字で固定する**（あとで Z が増えても変えない）。例：相手の原本は `F_v0.1.0_<相手> Original.docx`、7周回して送った直しは `F_v0.2.7_Axla Comments.docx`、その後に相手から来る返事は `F_v0.3.7_<相手> ….docx`。
- 三層にするのは、1つの名前で「どの世代の LEGAL.md で回したか（X）」「相手と何往復目か（Y）」「社内で何周検証したか（Z）」が分かるようにするため。相手から見ても、Y が往復の順に増えるので読み違えない。
- 検証役の指示文（prompts/reviewer-prompts.md）は、いまは SemVer のまま（MINOR＝学びの反映、PATCH＝言い回しの修正）。LEGAL.md の世代にそろえるかは Open Questions。
- 数え方の詳細と台帳の列は [docs/register.md](../docs/register.md)。
- .docx を gdoc に取り込み直す前に、gdoc の開いているコメントを**解決済みにする（消さない）**（scripts/resolve_comments.py）。Drive のコメントは取り込み直しても消えないので、こうしないと前のコメントと新しいコメントが二重になる。取り込んだ後、開いているコメントの数が changes JSON の comments の数と同じことを確かめる。
- 作業用の gdoc は、**送る版と同じ名前の gdoc**（`F_vX.Y.Z_Axla Comments`）にする。gdoc は社内用（提案とコメント入り）、.docx は相手に送るもの。拡張子だけが違う。版の中の社内の周回の状態は、その gdoc の版の履歴に残る。
- 次に Axla が送る版（Y＝4）を作るときは、前に送った版の gdoc（例 `F_v0.2.7_Axla Comments`）をコピーして作業し、送るときに、その時点の Z で `F_v0.4.<Z>_Axla Comments` と名前を付ける。前の版の gdoc は、送った版の社内の記録として残る。コピーで提案とコメントが引き継がれるかは要確認（実物で一度試して確かめる）。引き継がれなければ、scripts/ の道具で、その版の .docx から作り直して取り込む。

## Drive の構成

```
Legal/
└── <契約の種類>/
    └── yymmdd_<契約名>_<相手> ✕ Axla Inc./      … 契約フォルダ（F）。相手とは共有しない。契約書だけを置く
        ├── F_vX.1.0_<相手> Original.docx         … 相手の原本（受け取ったまま）
        ├── F_vX.1.0_<相手> Original              … その gdoc（読む用。中身の確認や検索に使い、書き換えない）
        ├── F_vX.2.Z_Axla Comments                … Axla の直しの社内用 gdoc。原本＋提案＋理由のコメント（作業はここで）
        ├── F_vX.2.Z_Axla Comments.docx           … 相手に送る清書・送った版の記録（変換しない。変更履歴もコメントもない）
        ├── F_vX.3.Z_<相手> ….docx                … 相手の返事（以降、往復ごとに Y を進める）
        ├── F_vX.4.Z_Axla Comments ／ .docx       … 次の直し（前の版の gdoc をコピーして作る）
        ├── F_Final.docx                          … 双方が合意した最終版（署名に回すもの。あるとき）
        └── F_Signed.pdf                          … 署名済み。これが入ったらループ終了

<利用側のリポジトリ>/loop/legal/contracts/<契約 ID>/   … 社内の記録。git に入れない（.gitignore）
    ├── loop-log.md                               … ループ記録（Markdown）
    ├── Redline Data.json                         … changes JSON
    └── 署名前の確認のスクショなど
```

- ファイル名は相手にも見えるので、英語を基本にする。形は「契約フォルダ名＋`_`＋版＋英語の役割名」。
- Gmail の添付名は120文字まで。長いときは役割名を短くする。
- 途中の直しは、ファイルを増やさず、その版の gdoc（`F_vX.Y.Z_Axla Comments`）に取り込む（前の状態は版の履歴に残る）。検証の記録は `loop/legal/contracts/<契約 ID>/loop-log.md` に書く。scratchpad などの一時フォルダだけに残さない。
- Drive の契約フォルダには契約書（相手との版の .docx と社内用の gdoc）だけを置く。記録（Loop Log・changes JSON・スクショ）は axla-inc の `loop/legal/contracts/<契約 ID>/` に置き、git には入れない（契約の本文が入るため）。
- 古いファイルをゴミ箱に移すときは、中身が版の gdoc と `loop-log.md` に移っているのを確かめてからにする。

## 標準の流れ：gdoc で先に確認 → 最終 OK で清書と下書き

開発のプレビューと同じ形にする。毎回 PDF を作ったり、清書や下書きを先に作ったりしない。

1. **社内用の gdoc だけを更新する。** 相手の返事が来た版なら、その版の gdoc（例 `F_v0.3.7_<相手> Comments`）に、こちらの直しを入れる。相手の変更を受けるところは受けた状態に、Axla の直しは提案＋理由のコメントにする。相手のコメントは消さずに見える状態で残す（解決済みにするなら、理由をコメントで返す）。受け取った .docx には触らない。
2. **内側のループで検証する**（致命的 0 で止まる。Z を数える）。この段階では、PDF の目視・清書の .docx・返信の下書き・台帳の「送付待ち」への更新はしない。
3. **司令塔に、gdoc のリンクと「何を変えたか」を3行で知らせて止まる。** 代表が gdoc を見て、直しを頼むか「最終 OK」を出す。
4. **最終 OK のあとで**：gdoc の名前を `F_vX.Y.Z_Axla Comments` に変える → 清書の .docx を作って置く → PDF に書き出して1回だけ目で確かめる → 返信の下書き（make_reply.py）→ check_draft.py → 台帳・Loop Log・push。

## 止める条件

- 内側：致命的 0件で送る前のゲートへ。重要の指摘は、直すか、Loop Log の「戻されたときの用意」に回す。
- 5周しても致命的が 0件にならない → G1。
- 本文を大きく直した周は、検証役を4体に戻す（小さな直しなら1体に4観点でよい）。

## 送る前のゲート

**相手に送るのは清書、社内の gdoc は履歴付き。** 相手が取り消し線やコメントを消す手間をなくすため（ホスピタリティ）。何を直したか・理由は、清書には入れず、make_reply.py が作るメール本文の一覧で伝える。

送る .docx（`F_vX.Y.Z_Axla Comments.docx`、清書。scripts/make_clean.py）について、下書きを作る前に確かめる。

- **清書になっている**：変更履歴（挿入・削除・書式の変更）0、取り消し線 0、コメントの印と部品 0。
- **文書のプロパティ**：作成者・最終更新者・表題・会社・独自のプロパティを消してある（make_clean.py）。
- **社内向けの混入**：メール本文の理由（＝社内 gdoc のコメントの文）が相手に見せてよい書き方になっている（プランの種類・G1 の話・社内の見立てを書かない）。相手向けのコメントは、すべてメール本文に入っている（make_reply.py の照合）。［修正］【要確認】などの社内の印がない。相手の前の版の変更履歴や、隠し文字が残っていない。
- **本文**：清書の本文が、最後に検証した直しと一致する（`view.py accept`）。清書を PDF に書き出して目で確かめる（雛形の空欄の下線などが残っていない、署名欄が言葉の途中で折れていない）。
- **添付名**：`F_vX.Y.Z_Axla Comments.docx`（n＝相手との境目をまたいだ回数）で、120文字以内。契約フォルダや gdoc のリンクは送らない。
- **下書き**（scripts/check_draft.py）：HTML の `<img>` が 0、画像のパーツが 0。添付の予定は契約書の1つだけ。返信の下書きには、相手のメールの引用（署名ロゴやボタンの画像を含む）が自動で付くので、残っていれば代表が Gmail の画面で引用部分を消す。代表が添付を付けたら、送る直前に「添付 1・画像 0」をもう一度確かめる。
- **送った後**：送信済みのメッセージを check_draft.py で調べ、添付が契約書の1つだけ・画像のパーツ 0 であることを確かめる。違えば INCIDENT として Loop Log とLEGAL.mdに記録する。

## 人間ゲート

人の手が入るのは、次の3つだけ。

| 呼び方 | いつ | だれが・何を |
|---|---|---|
| **G1**（事業の判断） | LEGAL.mdの「G1 に上げる」に当たるとき。5周しても致命的が 0件にならないとき | 代表が決める。目的の書き方、乙の表示（代表者名など）、生成 AI のプラン、LEGAL.mdの外の修正を受けるか断るか |
| **送信** | 送る前のゲートを通った後 | 代表が、Gmail の下書きに添付を付けて送信ボタンを押す（ループは下書きまで） |
| **G2**（署名） | Final に双方が合意した後 | 代表が署名する |

- 書き方は、spec・LEGAL.md・指示文で G1／送信／G2 にそろえる。
- サブセッションは AskUserQuestion を使わず、司令塔のセッションにまとめて聞く。

## 記録

### Loop Log（axla-inc の loop/legal/contracts/<契約 ID>/loop-log.md）

上から順に、次の節を置く。

1. いまの状態と次の一手（状態・現在の版・検証・相手との往復・次の一手・終わりの条件）
2. 各周の記録（周ごとに、検証役ごとの件数と指摘）
3. G1 の答え
4. 相手に戻されたときの用意（相手側の法務役が「条件付き」と見た所の文言）
5. 署名前の確認（代表の作業）
6. 変更点と理由（v1 → 最新の直し）
7. ループの状態（状態・版・周回などを、機械が読める形で1か所にまとめた節。別のファイルにはしない）
8. 学び（Signed の後に、LEGAL.mdへ PR で反映する候補）
9. 付録：境目の版（v1、v3 …）と最新の直しの「違う段落」（scripts/make_loop_log.py）

### 台帳（loop/legal/register.csv）

台帳は Drive ではなく、この git の `loop/legal/register.csv` に置く。全契約を1行ずつ。列の意味・ID の付け方・「人が触った回数」の数え方・更新するときは、[docs/register.md](../docs/register.md) に書いてある。相手の社名・担当者は書かない（NDA では契約の事実も機密）。

## 戻し方

- 版の gdoc（`F_vX.Y.Z_Axla Comments`）：Drive の版の履歴に前の状態が残る。前の状態の .docx をもう一度取り込めば戻る（新しいファイルは作らない）。
- ゴミ箱に移したファイル：30日以内なら Drive のゴミ箱から戻せる。
- Gmail の下書き：消した下書きは戻せないので、作り直す（本文は Loop Log から再現できる）。
- 送ってしまったメールは戻せない。だから送信は代表だけが押す。

## Gmail

- 返信は、相手が雛形を送ってきたメールの続き（同じスレッドへの返信）の下書きにする（`create_draft` の `replyToMessageId`）。
- スレッドの中の返信の下書きには、ループからファイルを添付できない（送り先の確認が済んでいないため、アプリが止める）。下書きは添付なしで作り、代表が Gmail の「ドライブから挿入」で `F_vX.Y.Z_Axla Comments.docx` を付けてから送る。
- 返信の下書きには、コネクタが相手のメールを引用として足す。その中の画像（署名ロゴ・共有通知のボタンなど）は、送信時に添付に変わる。下書きの本文を差し替えても引用は付き直す。送る前に代表が引用部分を消し、check_draft.py で画像 0 を確かめる。
- 契約フォルダを相手と共有しない（リンクではなく、添付で送る）。
- **メール本文の修正点は scripts/make_reply.py で作る。手で書かない。** 修正点の理由は、契約書の相手向けコメントの文をそのまま使うので、契約書とメールが一言一句つながる。下書きを作ったら、修正点の部分が道具の出力と1文字も違わないことを確かめる。
- 本文はセミカジュアルにして、代表の過去の返信のトーンに合わせる。主な修正を箇条書きにし、署名のやり方（電子契約にするか、押印して PDF でやりとりするか）をたずねて、1往復で進められるようにする。
- 別の道具（Gmail の権限を足したトークンなど）で、アプリが止めた操作を回り込まない。
